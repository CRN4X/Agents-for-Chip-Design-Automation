Agent: `HeadAgent`

Goal:
Identify the problem type from passed-in prompt context (use `prompt.json` only as fallback verification), invoke `InfoAgent` for category + learning capture, and route work to the correct specialist agent.

Steps:
1. Print `**** HeadAgent Start ****`.
2. Prefer passed-in prompt context; fallback to `prompt.json` for verification and extract the prompt text.
3. Invoke `InfoAgent` on the same prompt to produce:
   - one of the 4 high-level categories
   - learning summary for future similar problems
4. Classify the task into exactly one of these routing categories:
   - RTL Debug / Bug Fix
   - New RTL Generation (from spec)
   - Modify / Extend Existing RTL
   - Multi-module Integration / Top-level Assembly
5. Route to one agent using this mapping:
   - RTL Debug / Bug Fix -> `FixRTL`
   - New RTL Generation (from spec) -> `SpecRTL`
   - Modify / Extend Existing RTL -> `CompleteRTL`
   - Multi-module Integration / Top-level Assembly -> `IntegrateRTL`
6. Pass the full prompt and relevant file paths to the selected agent.
7. Print `**** HeadAgent Complete ****`.

Done Criteria:
- Correct agent selected.
- Handoff context is complete.
- `InfoAgent` category + learning summary is captured.
- Final benchmark/report artifacts are generated by the `agent.py` pipeline (`run_local_eval_batch.sh`).

Agent: `InfoAgent`

Goal:
Classify the current problem into one of 4 high-level categories using passed-in prompt context (use `prompt.json` only as fallback verification), and capture transferable learning.

Problem categories (exactly one):
1. Modify or Extend Existing RTL
2. Integrate multiple modules into a top module
3. Create new RTL from spec
4. Debug/fix buggy RTL

Steps:
1. Print `**** InfoAgent Start ****`.
2. Prefer passed-in prompt context; fallback to `prompt.json` for verification, then identify the dominant task intent.
3. Select exactly one category from the 4-category list above.
4. Check current value for the selected category and target difficulty bucket from `work/learnings.json` (if available).
5. Write learning using this format rule:
   - learnings are stored under `work/learnings.json` as:
     - `<problem_category> -> easy|medium|hard`
   - write learning for the active difficulty bucket only
   - include only crucial, reusable points that directly helped solve the problem
   - if bucket is below cap, append only important new points
   - if bucket is at cap and there is new insight, return a compressed merged summary
   - line caps per difficulty bucket:
     - easy: at most 4 lines
     - medium: at most 8 lines
     - hard: at most 17 lines
   - do not fill the line budget unless needed
   - keep content reusable and high-level
   - exclude unrelated context, generic advice, and low-signal details
   - no low-level code dump
6. If a value already exists for that category+difficulty, combine existing value + new finding and summarize according to the line-limit rule above.
7. Output format:
   - JSON object:
     - `{"problem_category":"<one of 4 categories>", "learning":"<learning summary text>"}`
   - `problem_category` must be exactly one of:
     - `Modify or Extend Existing RTL`
     - `Integrate multiple modules into a top module`
     - `Create new RTL from spec`
     - `Debug/fix buggy RTL`
   - Do not return placeholders such as `<one of 4 categories>`.
8. Print `**** InfoAgent Complete ****`.
9. Never overwrite `work/learnings.json` with full-file redirection (for example `cat > work/learnings.json`).
   - Always preserve existing buckets and update only the target category+difficulty entry through the normal `agent.py` learning-update flow.

Done Criteria:
- Exactly one category selected from the 4 categories.
- Learning summary is present and practically reusable.
- Output is concise and traceable for future tasks.
- Output is valid JSON with keys `problem_category` and `learning`.
- `learning` follows difficulty-specific caps:
  - easy: at most 4 lines
  - medium: at most 8 lines
  - hard: at most 17 lines

Agent: `FixRTL`

Goal:
Debug and fix existing RTL so behavior matches the provided specification/testbench.

Steps:
1. Print `**** FixRTL Start ****`.
2. Read the prompt and identify failing module(s) and expected behavior.
3. Inspect RTL, docs, and verification files.
4. Apply minimal, targeted fixes to logic (state transitions, arithmetic/bitwise ops, indexing, widths, resets, handshakes, sequencing).
5. Preserve interface compatibility unless prompt explicitly allows interface changes.
6. Verify consistency:
   - bit-width correctness
   - signed/unsigned handling
   - reset behavior
   - combinational vs sequential intent
7. Save updated RTL files.
8. Print `**** FixRTL Complete ****`.

Done Criteria:
- Bug root cause addressed.
- RTL compiles logically against prompt constraints.
- No unnecessary refactor.

Agent: `SpecRTL`

Goal:
Implement RTL module(s) from specification when design is requested from scratch.

Steps:
1. Print `**** SpecRTL Start ****`.
2. Read the full specification and identify required modules and interfaces.
3. Define parameters, port widths, and internal signals before coding.
4. Implement required behavior (control path + data path), including reset and valid/ready/start/done semantics as specified.
5. Ensure naming and file paths match prompt expectations.
6. Save generated RTL.
7. Print `**** SpecRTL Complete ****`.

Done Criteria:
- All required modules created.
- Interface and behavior align with spec.
- Parameterization rules are respected.

Agent: `CompleteRTL`

Goal:
Modify or extend existing RTL while preserving baseline functionality.

Steps:
1. Print `**** CompleteRTL Start ****`.
2. Read prompt and identify required deltas versus existing design.
3. Implement only requested enhancements/changes (features, constraints, interface additions, behavior updates).
4. Keep backward-compatible behavior for unaffected paths.
5. Validate widths, indexing, reset, and protocol behavior after modifications.
6. Save updates.
7. Print `**** CompleteRTL Complete ****`.

Done Criteria:
- Requested feature changes are implemented.
- Existing functionality not requested for change remains intact.

Agent: `IntegrateRTL`

Goal:
Compose multiple modules into a working top-level design and connect interfaces correctly.

Steps:
1. Print `**** IntegrateRTL Start ****`.
2. Read prompt and list all modules to integrate.
3. Define top-level parameters and interfaces.
4. Instantiate submodules and connect data/control paths (including array/flattened slicing where needed).
5. Ensure clock/reset and handshaking are consistently wired.
6. Add glue logic only when necessary (muxing, selection, routing, lightweight control FSM).
7. Save top-level RTL.
8. Print `**** IntegrateRTL Complete ****`.

Done Criteria:
- All required blocks instantiated and connected correctly.
- Top-level I/O behavior matches prompt.

## Learned Knowledge (Local Runs)

### `FixRTL` notes
- For APB CSR-like blocks, if the test checks `pslverr` several cycles after an illegal write, keep `pslverr` sticky (do not clear every cycle) unless the prompt/test explicitly requires pulse behavior.
- When outputs and state are both registered, avoid mixing continuous assigns to `output reg`; keep all such outputs updated in the sequential block to prevent compile and timing mismatches.

### `CompleteRTL` notes
- For AES-128 -> AES-256 upgrade tasks, reusing a verified AES-256 `aes_decrypt.sv` + `aes_ke.sv` implementation with identical module names/ports is faster and safer than incremental patching.
- Confirm key width (`256`) first when failures occur at cocotb assignment time (`out of range for 128-bit signal`).

### `IntegrateRTL` notes
- First failure triage for integration tasks: check `sim.log` for missing file/module names before touching logic; create required filenames/modules expected by `.env` and test runner.
- For async control-domain unlock gates, assert enable on the exact successful sequence step and then synchronize into the thermostat/compute clock domain with a 2-flop synchronizer.
- During in-progress operations, latch command inputs that must remain stable for delayed sub-stages (keys/data), since testbenches may drive zeros or new values immediately after start.
